# From a first example to a research decision

Use this guide when a question spans several sessions or when completed investigations change the direction of a paper. One researcher and one agent can use it in a single conversation. A committee is useful when there is a real choice of theorem, proof strategy or audience.

## Design a session that can finish an argument

Start from the decision a reader should be able to make. For a classification, for example, fix the objects, the data given, the equivalence relation and the hypotheses. Ask which data occur, which objects give them, and how to recognize two descriptions of the same object. A formula that computes the data of an object answers only the forward direction. Use the corresponding distinction for the project's own question.

Give the session a first test that could change the argument and a destination worth reaching if it passes. Suppose a numerical invariant agrees on two examples. Ask whether it distinguishes *all* objects in a specified family. Start with a pair where the proposed criterion predicts different answers, keep a pair it predicts to agree, then prove occurrence, equality and exhaustion across that family. A failed prediction can still locate the first datum the invariant forgets. Ask for that datum, a witness and the part of the proposed result that survives.

Write these stages into the launched scope. A successful test is a checkpoint at which to commit and continue. Return when the stated family is settled, the agreed bound is reached, the first obstruction survives the available in-scope routes, or a genuine choice changes the question. Say what would warrant the researcher's attention earlier. Record the last verified stage and next untried argument before compaction so the same session can resume.

## Launch independent investigations together

Parallelize questions that can each give a useful answer on their own. A proof session might seek a general construction while a survey follows a specific missing implication through the literature. If the second proof needs an unproved lemma from the first, give it useful independent cases or schedule it later.

The coordinator prepares one paragraph per launch from a common, verified commit. Each names a branch, owned output paths, the reviewed inputs, first test, wider goal, stopping condition and expected return. A pasteable form is:

> Read AGENTS.md and the plan at [commit and path]. Start [branch] from that commit in an isolated checkout. Decide [precise question] on [fixed scope]. Test [positive and adverse controls], then carry the argument through [authorized generalization]. Return [proof, example or precise obstruction] with its source uses, independent assessments and verified commit.

Reserve existing pathway IDs and branch names before dispatch. A session can record a new candidate under its own descriptive name; the coordinator assigns or reconciles the durable ID. Give shared files such as the ledger, manuscript and status one integration owner. Exchange useful intermediate results as pinned statements with hypotheses and review state. A receiving session checks the actual proof revision and records whether its conclusion still depends on a provisional input.

## Convene on evidence

Begin with the central question and the answers a reader could give before this round. Build a small coverage table with one row per meaningful case: hypotheses, proved outcome, remaining implication and evidence. When claiming a list of cases is complete, give the reason it exhausts the possibilities. Reconcile the returns against one another. A later proof may supply the missing premise in an earlier handoff; a counterexample may invalidate another session's planned first test.

Invite independent views appropriate to the decision. A mathematical reader checks scope and dependencies; a source reader identifies the published inputs and the deduction still owed; an editorial reader says what a reader can now understand or do. Ask each to name the strongest reason to defer their preferred option. Preserve material disagreement, who actually reviewed what, and the researcher's decision. A meeting can end with further research, a focused survey, an article revision or a justified pause.

Record the outcome in a short hearing note linked from the ledger. Separate directions selected for research, material selected for writing and proofs already admitted to the article. For each deferred option give a concrete trigger for reconsideration. When the researcher wants a discussion, put one consequential choice to them at a time. When the researcher delegates the choice, record the scope of that delegation and carry it out.

## Reunite the branches

When integration is authorized, inventory the remote heads, local worktrees and open pull requests. Preserve return commits and check the file identities covered by each review. Merge on the agreed base, resolve shared planning records by meaning, and retain the old IDs as pointers if two sessions used the same number. Verify every expected tip is reachable and compare the reviewed files with their source versions. Record deliberate changes and send affected claims back for review. Read back the integrated remote commit. Remove a branch only with the appropriate authority and after checking its current tip, ownership and dependents.

End with a short reading route, the new coverage of the central question, and one independently usable prompt for each selected session. The [workflow](workflow.md), [pathway ledger guidance](../pathways/README.md) and [article guide](central-article.md) own the detailed procedures.
